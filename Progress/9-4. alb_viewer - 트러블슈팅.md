# alb_viewer 구성 및 배포하는 도중 발생한 장애

## 1. ECR에 있는 이미지로 pod 띄웠을 때 ImagePullBackOff 장애 발생

### 장애 현상 

docker 이미지 생성 후 AWS ECR에 올린 뒤 해당 이미지를 이용해 deployment를 만들었고, pod가 생성되는 과정에서 ImagePullBackOff 장애가 발생

```bash
Events:
  Type     Reason     Age                    From               Message
  ----     ------     ----                   ----               -------
  Normal   Scheduled  6m43s                  default-scheduler  Successfully assigned monitoring/alb-log-viewer-58ff679b98-x9m95 to ip-10-0-2-124.ap-northeast-2.compute.internal
  Normal   Pulling    3m55s (x5 over 6m42s)  kubelet            spec.containers{alb-log-viewer}: Pulling image "245067526307.dkr.ecr.ap-northeast-2.amazonaws.com/alb-log-viewer:1.0"
  Warning  Failed     3m54s (x5 over 6m42s)  kubelet            spec.containers{alb-log-viewer}: Failed to pull image "245067526307.dkr.ecr.ap-northeast-2.amazonaws.com/alb-log-viewer:1.0": rpc error: code = NotFound desc = failed to pull and unpack image "245067526307.dkr.ecr.ap-northeast-2.amazonaws.com/alb-log-viewer:1.0": no match for platform in manifest: not found
  Warning  Failed     3m54s (x5 over 6m42s)  kubelet            spec.containers{alb-log-viewer}: Error: ErrImagePull
  Warning  Failed     100s (x20 over 6m42s)  kubelet            spec.containers{alb-log-viewer}: Error: ImagePullBackOff
  Normal   BackOff    87s (x21 over 6m42s)   kubelet            spec.containers{alb-log-viewer}: Back-off pulling image "245067526307.dkr.ecr.ap-northeast-2.amazonaws.com/alb-log-viewer:1.0"
```

### 장애 원인

장애 원인 핵심은 "no match for platform in manifest: not found" 이 부분임. <br>
즉, mac에서 만든 docker 이미지의 cpu 아키텍처와 eks node의 cpu 아키텍처가 달라서 발생한 장애임.

ma에서 생성한 이미지 : ARM64 <br>
EKS Node : x86_64 / amd64

```bash
EKS Node (amd64)
      ↓
ECR에서 이미지 pull
      ↓
ARM64 이미지 발견
      ↓
❌ no match for platform in manifest
```

### 장애 해결

이미지를 linux/amd64로 다시 빌드해서 ECR에 올리면 장애 해결

```bash
docker buildx build \
  --platform linux/amd64 \
  -t 245067526307.dkr.ecr.ap-northeast-2.amazonaws.com/alb-log-viewer \
  --push \
  .
```

ECR에 다시 올렸다면, 기존에 장애난 pod를 delete하면 새로운 pod가 정상적으로 생성됨

```bash
kubectl delete pod -n monitoring -l app=alb-log-viewer
```

## 2. Ingress.yaml 변경 후 새로운 ALB가 생성되었고, externalDNS가 있었음에도 Route53의 ALB 정보가 변경되지 않는 장애 발생

### 장애 현상 

기존 Ingress에서 Ingress group을 추가하여 apply 후 신규 ALB가 생성됨. <br>
externalDNS가 있는 상태여서 자동으로 Route53 정보도 변경될것이라 생각됐지만, 여전히 이전 ALB를 바라보고 있어서 장애 발생

```bash
# Ingress yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: application-ingress
  namespace: application
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/group.name: heewoon1204
spec:
  ingressClassName: alb
  rules:
    - host: www.heewoon1204.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx
                port:
                  number: 80

# external-dns depolyment 
# 확인 명령어
kubectl get deployment external-dns -n external-dns -o yaml | grep -A 20 "args:"

# 결과
      - args:
        - --log-level=info
        - --log-format=text
        - --interval=1m
        - --source=service
        - --source=ingress
        - --policy=upsert-only
        - --registry=txt
        - --txt-owner-id=hw-infra-eks-cluster
        - --provider=aws
        env:
        - name: AWS_DEFAULT_REGION
          value: ap-northeast-2
        image: 602401143452.dkr.ecr.ap-northeast-2.amazonaws.com/eks/external-dns:v0.21.0-eksbuild.6
        imagePullPolicy: IfNotPresent
        livenessProbe:
          failureThreshold: 2
          httpGet:
            path: /healthz
            port: http
            scheme: HTTP
```

### 장애 원인

"-policy=upsert-only" 설정은 기존 레코드를 절대 덮어쓰지 않음 <br>


### 장애 해결

1. 수동으로 route53 record를 삭제해야 external-dns가 자동으로 현재 기준의 ALB로 등록함

2. external-dns의 policy를 sync로 변경하면 자동으로 덮어씌워줌
