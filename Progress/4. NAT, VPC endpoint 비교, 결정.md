# NAT Gateway vs VPC Endpint

## 비교

- NAT Gateway : aws 서비스마다 endpoint 찾아서 만들지 않아도 되서 설정이 단순하나, endpoint 보다 보안에 약하고 비용이 비쌈
- VPC Endpoint : aws 서비스 중심의 private 환경을 만들 수 있어 보안에 좋으나, 필요한 서비스마다 만들어야해서 복잡하고 관리가 복잡해짐.
                또한, subnet 별로 ENI를 만들어서 subnet이 많을 수록 비용이 많이 나감

| 구분           | **NAT Gateway**                           | **VPC Endpoint**                                        |
| ------------ | ----------------------------------------- | ------------------------------------------------------- |
| 기본 역할        | Private Subnet의 리소스가 **인터넷으로 나갈 수 있게** 해줌 | Private Subnet의 리소스가 **특정 AWS 서비스에 Private하게 접근**하도록 해줌 |
| 접근 범위        | 인터넷 전체 + AWS 서비스                          | 설정한 특정 AWS 서비스                                          |
| 인터넷 접근       | ✅ 가능                                      | ❌ 불가능                                                   |
| AWS 서비스 접근   | ✅ 가능                                      | ✅ 지정한 서비스만                                              |
| Public IP 필요 | NAT Gateway에 Public IP 필요                 | ❌ 불필요                                                   |
| 구성 방식        | Private RT → NAT Gateway → IGW            | Interface ENI 또는 Gateway Route                          |
| 보안           | 인터넷으로 나갈 수 있어 상대적으로 넓음                    | 특정 서비스만 허용 가능해 상대적으로 제한적                                |
| 비용           | 시간당 비용 + 데이터 처리 비용                        | Interface: ENI 시간당 + 데이터 처리 / Gateway: 무료               |
| AZ 구성        | 실무에서는 AZ별 NAT Gateway 권장                  | Interface Endpoint도 일반적으로 AZ별 구성 권장                     |
| 관리           | 비교적 단순                                    | Endpoint 종류가 많아지면 관리 복잡                                 |
| 확장성          | 인터넷의 다양한 서비스에 접근 가능                       | 필요한 AWS 서비스마다 Endpoint 추가 필요                            |
| 대표 사용 예      | 패키지 설치, 외부 API 호출, 인터넷 접근                 | ECR, S3, STS, EKS, CloudWatch 등                         |
| Private 통신   |  인터넷/NAT 경유                              | ✅ AWS 네트워크 내부에서 통신                                      |
| NAT 장애 영향    | NAT 장애 시 해당 경로 사용 불가                      | Endpoint별로 독립적으로 관리                                     |

<br>

## 고민

### 1. 보안에 민감한 환경인가??

보안에 민감하다면 외부와 접근이 차단되고 AWS 서비스가 뚫려있는 endpoint를 사용해야하지만, 현재 프로젝트는 개인 장애대응 관련 프로젝트로 보안에 민감하지 않음.

<br>

### 2. 보안에 민감하지 않다면, 비용 절감할 수 있는 선택은 어떤 것인가??

| 항목           | **NAT Gateway**  | **VPC Endpoint** |
| ------------ | ---------------------- | ------------------- |
| 시간당 요금   | $0.045/hr (게이트웨이 1개) | $0.01/hr (엔드포인트 1개 × AZ당) |
| 데이터 처리 요금   | $0.045/GB |  $0.01/GB (첫 1PB)|

단순하게 개별 비용으로 보면 NAT Gateway가 $0.045/hr로 endpoint보다 많이 비싸게 느껴짐. 그래서 처음에는 NAT를 빼고 endpoint로 아키텍처를 구성하려고 했음.

EKS 환경에서 필수적으로 VPC Endpoint 6개가 있는데 그중 5개가 Interface 타입으로 비용을 지불해야하는 리소스임. <br>
또한 private subnet이 2개기 때문에 endpoint 별로 각각 2개씩 필요해서 비용도 2배가 되는 현상 발생 <br>
이외에도 권장 endpoint까지 하면 비용이 더 추가될 확률이 있음.

그 기준으로 다시 계산해보면, VPC Endpoint 더 많은 비용이 나감

| 항목           | **NAT Gateway (2개)**  | **VPC Endpoint  (5개 × 2 AZ)** |
| ------------ | ---------------------- | ------------------- |
| 월 고정 비용   | $$65.70 | 	$73.00 |

<br>

### 3. NAT Gateway를 하나만 써서 비용을 더 줄일 수는 없는 것인가??

가용성을 위해 zone별로 NAT Gateway를 사용해야하지만, 하나의 zone에만 있어도 private 환경에서 외부로 통신이 가능함. <br>
단, Cross-AZ 데이터 전송 비용($0.01/GB)이 발생함.

데이터 전송이 많지 않은 개인 프로젝트이기 때문에 Cross-AZ 데이터 전송 비용은 고려하지 않아도 될 정도지만 가용성의 문제가 생길 수 있음. <br>
NAT가 있는 zone에 장애가 나면 장애나지 않은 zone에는 NAT가 없기 때문에 통신에 문제가 생길 수 있고, 


<br><br>


## 결정

FIP처럼 zone 자체 장애를 테스트할 때 문제가 있을 수 있지만, 최종적으로 비용을 고려했을 때 하나의 zone에만 NAT 사용

```bash
AZ-A                    AZ-C
 │                       │
Private A             Private C
 │                       │
 └──── NAT-A ────────────┘
             │
          Internet
```

## 별첨

EKS 환경에서 필수로 필요한 VPC Endpoint 및 권장 Endpoint

### 1. 필수 Endpoint

| Endpoint 서비스명                    | 타입          | 용도                                       
| -------------------------------- | ----------- | ------------------------------------------ | 
| `com.amazonaws.<region>.ec2`     | Interface   | 노드 부팅 시 인스턴스 정보 조회, ENI 관리 (VPC CNI)       | 
| `com.amazonaws.<region>.eks`     | Interface   | kubelet → EKS Control Plane 등록, 클러스터 정보 조회 | 
| `com.amazonaws.<region>.sts`     | Interface   | 노드 IAM Role 인증, IRSA 토큰 발급                 |  
| `com.amazonaws.<region>.ecr.api` | Interface   | ECR 이미지 메타데이터 API 호출                       |   
| `com.amazonaws.<region>.ecr.dkr` | Interface   | ECR Docker Registry를 통한 이미지 Pull           |   
| `com.amazonaws.<region>.s3`      | **Gateway** | ECR 이미지 레이어 데이터 다운로드                       | 



### 2. 권장 Endpoint

| Endpoint 서비스명                       | 타입        | 용도                                           |
| ----------------------------------- | --------- | -------------------------------------------- |
| `com.amazonaws.<region>.logs`       | Interface | CloudWatch Logs로 컨테이너/노드 로그 전송               |
| `com.amazonaws.<region>.monitoring` | Interface | CloudWatch Metrics 전송 (Container Insights 등) |
